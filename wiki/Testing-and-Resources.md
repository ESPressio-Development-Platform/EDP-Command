# Testing and Resources

The v1 acceptance gate is intentionally broader than compilation.

Host coverage progressively verifies admission capacity, lifecycle transitions, cancellation, finite waiting, Handle move/release/retention, exactly-once Response extraction, shutdown/quiescence, terminal Outcome observation, Handler success/rejection/failure, F4 LocalOnly/RemoteOnly/LocalAndRemote scope semantics and fake outbound completion. The F4 contract test verifies statically distinct domain result shapes, lack of remote scope on `InboundAdmission`, and that a negative outcome in one LocalAndRemote domain does not suppress the other operation. Compile-time invalid `ResourcePlan` configurations are rejected by static assertions; missing and duplicate Handler providers are also compile-time rejection cases.

`tests/run_tests.py` consumes sibling EDP repositories from the coherent local checkout. `CXX` selects the host compiler and optional `CXXFLAGS` are appended to every host compile so the same runner can exercise configurations such as ASan/UBSan. In addition to lifecycle and F4 scope contracts, it builds and executes `tests/host/resource_measurement.cpp`, which reports deterministic `sizeof(Runtime)` measurements for minimum, small, representative and high bounded resource plans. This makes the memory delta associated with invocation/queue/concurrency choices visible and repeatable without dynamic allocation.

The first post-H16 dependency-ordered host regression on 2026-09-27 passed EDP-Memory, EDP-Threading and EDP-Command. EDP-Command reported Runtime measurements of 112, 176, 360 and 664 bytes for the minimum, small, representative and high fixtures respectively, and confirmed missing/duplicate Handler rejection at compile time.

Target demos exist for each logical demonstration in all Policy/V2 required forms: Arduino IDE, PlatformIO Arduino-ESP32 and PlatformIO ESP-IDF. `ExecutionDomainScope` specifically demonstrates that both selected domains participate independently even when the local operation reports `NoCapacity`. The PlatformIO projects use the PIOArduino platform and sibling checkout dependencies so repository topologies can be tested coherently.

`.github/workflows/validation.yml` mirrors the maintained automated surfaces with GCC/Clang host suites, ASan/UBSan host coverage, and PlatformIO Arduino/ESP-IDF builds for every maintained demo. Under current Policy this workflow is a maintained CI definition; RPI400 is the authoritative executable validation appliance.

The progressive acceptance sequence is Memory, Threading, Command host/resource, then Command target-demo builds. H1-H16 are locked architecture; failures are corrected against those decisions rather than by silently changing the contract. A fresh embedded target gate remains required after the final V2/static reconciliation.
